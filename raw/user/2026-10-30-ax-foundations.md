# AX 개발의 필수 기본 지식

이 문서에서 AX는 **AI를 활용해 개발 업무의 입력·실행·검증 방식을 개선하는 것**이라는 작업상 정의를 사용한다. 업계 전체의 단일 표준 정의라고 주장하지 않는다.
공식 문서·명세·원 논문을 읽고 한국어로 정리한 연구 노트이며, 원문 전문이나 검증을 마친 위키 페이지가 아니다.
검증일은 **2026-10-30, 한국 시간 기준**이다. 모델 이름·API 기능·요금은 바뀔 수 있으므로 실제 도입 시 다시 확인한다.

## 1. 먼저 구분할 것: 생성, 실행, 검증

LLM이 답을 만드는 일과 도구가 실제 동작하는 일은 구분해야 한다. 도구 호출에서는 모델이 호출과 인수를 제안하고, 애플리케이션이 실행한 결과를 다시 모델에 전달한다. [공식 도구 호출 흐름](https://developers.openai.com/api/docs/guides/function-calling)

따라서 “코드를 고쳤다”, “테스트가 통과했다”, “배포했다”는 문장만으로 실제 수행을 확인할 수 없다. 이 저장소에서는 각각 파일 변경, 테스트 실행 결과, 게시된 커밋으로 확인하는 운영 방식을 권한다. 이는 위 도구 호출 구조를 개발 검증에 적용한 제안이다.

학습 목표: 모델의 제안과 시스템의 실제 상태를 따로 설명할 수 있어야 한다.

## 2. 토큰과 컨텍스트: 얼마나 많이 넣느냐보다 무엇을 넣느냐

모델은 입력과 출력을 토큰 단위로 처리한다. 토큰은 단어와 동일하지 않으며 텍스트 외 입력도 토큰으로 계산된다. 문자 수의 대략적인 환산을 한국어의 정확한 계산으로 사용하지 않는다. [Google 토큰 안내](https://ai.google.dev/gemini-api/docs/tokens)

컨텍스트는 현재 요청에서 모델이 사용할 수 있는 지시·자료·대화·도구 결과의 범위로 이해한다. 대화를 길게 이어간다는 이유만으로 모든 과거 자료를 정확히 기억한다고 가정하지 않는다. 필요한 지식은 파일과 근거로 보존하는 것이 이 볼트의 운영 선택이다.

실무 제안: 요청에 목표, 관련 코드와 자료, 제약, 완료 조건을 넣고 관계없는 전체 저장소를 매번 전달하지 않는다. 입력 크기는 공급자의 토큰 계산 기능이나 사용량 정보로 확인한다. [토큰 계산 방법](https://ai.google.dev/gemini-api/docs/tokens)

## 3. 프롬프트: 역할 이름보다 작업 계약

공식 프롬프트 지침은 명확한 지시와 반복적인 개선을 강조한다. 한 번 쓴 프롬프트를 보편적인 정답으로 취급하지 않는다. [Google 프롬프트 설계](https://ai.google.dev/gemini-api/docs/prompting-strategies)

개발 작업에는 다음을 명시하는 방식을 권한다.

- 입력: 실제로 읽어야 할 코드·문서·원문.
- 목표: 사용자가 보게 될 결과와 유지할 동작.
- 범위: 수정할 수 있는 경로와 제외할 자료.
- 완료 조건: 확인할 결과와 실행할 검사.
- 불확실성: 근거가 없을 때 보류하거나 질문할 조건.

예: “공개 예제의 설정 폼의 실패 시 입력을 유지해 주세요. 관련 폼과 API 처리를 읽고, 성공·실패 동작을 확인해 주세요. 실제 실제 개인정보는 사용하지 마세요.” 이 문장은 학습용 제안이며 실행 결과가 아니다.

## 4. 구조화 출력: 모양을 맞추는 것과 사실이 맞는 것은 다르다

JSON Schema 기반 출력은 필드·타입 같은 형식을 안정적으로 다루는 데 도움을 준다. 그러나 구조화된 응답에도 내용 오류가 있을 수 있다. [OpenAI 구조화 출력과 오류 처리](https://developers.openai.com/api/docs/guides/structured-outputs)

실무 제안: 타입 검증 외에도 허용된 출처 ID인지, 링크가 입력에 실제 있었는지, 날짜가 타당한지, 같은 항목이 중복되지 않았는지 코드로 검사한다. 생성된 중요도나 해석은 별도로 검토한다.

학습 목표: “유효한 JSON”과 “근거가 있는 주장”을 각각 검증할 수 있어야 한다.

## 5. 워크플로와 에이전트

Anthropic은 정해진 코드 경로로 LLM·도구를 조합하는 워크플로와, 모델이 진행 과정과 도구 사용을 동적으로 결정하는 에이전트를 구분한다. 이는 유용한 설계 구분이며 모든 제품의 용어가 같다는 뜻은 아니다. [공식 설계 설명](https://www.anthropic.com/research/building-effective-agents)

이 볼트의 일일 수집 → 요약 → 검증 → 커밋은 정해진 워크플로다. 사람이 요청한 범위의 자료를 읽고 주제별 노트를 선택해 갱신하는 작업은 더 많은 판단을 에이전트에 맡긴다. 이는 위 정의를 현재 작업에 적용한 해석이다.

실무 제안: 먼저 단순한 단계를 만들고, 모델에게 맡길 선택이 실제로 있을 때 자율성을 늘린다. 실행 시간·호출 횟수·종료 조건을 함께 정한다.

## 6. RAG와 누적 위키

RAG 원 논문은 모델 내부 지식과 검색 가능한 외부 메모리를 결합하는 접근을 제시한다. 검색으로 가져온 자료를 생성에 활용한다는 원리를 먼저 이해하면 된다. 특정 벡터 데이터베이스 도입부터 시작할 필요는 없다는 것은 이 저장소의 학습 제안이다. [RAG 원 논문](https://arxiv.org/abs/2005.11401)

Karpathy의 LLM Wiki는 원자료와 별도로 연결된 지식 페이지를 지속적으로 작성·갱신하는 운영 패턴이다. 이는 아이디어 제안이며 RAG보다 우수하다는 비교 실험의 증거는 아니다. [LLM Wiki 원문](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

이 볼트에서는 raw에 자료를 쌓고 사람이 수동으로 위키화를 요청한다. 링크만 저장한 자료는 원문을 저장한 자료와 다르다. 링크 대상이 삭제되거나 변경되면 과거 내용을 복원할 수 없으므로 열람 여부와 확인 날짜를 기록하는 편이 좋다.

## 7. MCP, Agent Skills, AGENTS.md의 서로 다른 역할

**MCP**는 AI 애플리케이션을 외부 데이터·도구·시스템에 연결하는 공개 표준이다. 어떤 절차로 업무를 수행할지 자체를 모두 정해주는 규칙은 아니다. [MCP 공식 소개](https://modelcontextprotocol.io/docs/2026-07-28/getting-started/intro)

**Agent Skills**는 전문 지식과 작업 흐름을 `SKILL.md` 및 선택적인 스크립트·참고 자료로 묶는 형식이다. 필요한 시점에 세부 지침을 읽는 방식으로 설명된다. [Agent Skills 공식 소개](https://agentskills.io/home)

**AGENTS.md**는 프로젝트의 빌드·테스트·작업 관례 등 코딩 에이전트가 알아야 할 맥락을 두는 파일이다. [AGENTS.md 공식 설명](https://agents.md/)

이 저장소에 적용하면 MCP는 접근 수단, 스킬은 수동 위키 처리 절차, AGENTS.md는 저장소 공통 작업 규칙으로 구분해 생각할 수 있다. 이것은 이해를 위한 대응 관계이며 접근 권한이나 보안 경계를 대신하지 않는다.

## 8. 평가: 테스트와 사람 검토를 함께 설계하기

생성형 시스템은 같은 입력에도 결과가 달라질 수 있다. OpenAI의 평가 지침은 작업에 맞는 평가 기준, 대표 사례, 지속적인 평가를 다룬다. [평가 모범 사례](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

이 볼트에 권하는 평가 항목은 다음과 같다.

- 구조 검사: 필수 필드, 유효한 경로, 존재하는 출처 링크.
- 내용 검사: 주장이 인용한 자료에 의해 뒷받침되는지.
- 유용성 검사: 뉴스 재진술을 넘어 실제 결정에 도움이 되는지.
- 실패 검사: 근거 없음·빈 자료·상충 정보·접근 실패를 정직하게 처리하는지.
- 회귀 검사: 프롬프트나 모델을 바꿔도 이전 사례가 유지되는지.

코드 테스트 통과는 동작 계약에 대한 증거이며 AI 해석 전체의 진실성을 보장하지 않는다. 사람은 특히 변경된 판단과 근거가 약한 주장을 읽는 역할을 맡는 것이 좋다.

## 9. 권한, 프롬프트 주입, 비밀 자료

도구를 연결하면 정보 접근과 실제 변경이 가능해진다. MCP 보안 문서는 권한 범위 최소화, 토큰 처리, SSRF와 세션 탈취 등의 위험을 다룬다. 연결 가능하다는 것과 필요한 권한을 부여해야 한다는 것은 구분한다. [MCP 보안 지침](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)

외부 문서에 적힌 명령은 사용자 지시와 구분해야 한다. 자료에 “키를 보내라”나 “이 파일을 실행하라”가 있다고 작업 권한으로 해석하지 않는 것이 이 저장소의 원칙이다. 모델에게 주의 문구를 주는 것만으로 완전한 방어가 된다고 가정하지 않는다.

실무 제안: 읽기와 쓰기 권한을 분리하고, 허용 경로·출처를 코드로 제한하며, 공개 볼트에는 인증 키·회사 소스·개인정보를 넣지 않는다. 중요한 결과를 사람이 확인하도록 하는 접근은 공급자의 안전 지침과도 연결된다. [OpenAI 안전 모범 사례](https://developers.openai.com/api/docs/guides/safety-best-practices)

## 10. Git, 작은 변경, CI는 AX의 검증 기반

Git은 변경 이력과 이전 버전을 추적하며 브랜치로 변경을 제안할 수 있게 한다. AI가 수정한 결과도 같은 방식으로 누가·무엇을·왜 바꿨는지 검토한다. [Git 공식 안내](https://docs.github.com/en/get-started/using-git/about-git)

GitHub Actions는 저장소 이벤트에 따라 빌드·테스트 등의 작업을 실행하는 CI/CD 기능이다. 따라서 “AI가 확인했다고 말함” 대신 실제 검사 결과를 남기는 데 사용할 수 있다. [GitHub Actions 공식 소개](https://docs.github.com/en/actions/get-started/understand-github-actions)

실무 제안: 한 번의 변경 목적을 작게 잡고 변경 전후의 동작을 비교한다. 사람이 검토할 수 없는 규모의 변경을 한 번에 생성하면 검증이 어려우므로, 코드 생성 속도와 별도로 검토 가능성을 관리한다.

## 11. 웹 개발에 적용하는 우선순위

아래 항목은 위 공식 자료를 현재 환경에 적용한 **제안**이며 효과를 측정한 결과가 아니다.

1. 공개 예제 화면 하나를 대상으로 성공·실패·권한 없음 상태를 설명하게 한다.
2. 폼 검증과 오류 발생 후 입력 유지 동작이 요구사항과 일치하는지 확인한다.
3. 서버 데이터 캐시와 화면 상태의 경계를 변경 전후로 확인한다.
4. 공통 UI를 바꿀 때 실제 소비 화면과 영향 범위를 함께 확인한다.
5. 공개 예제의 문서화·테스트 보조부터 시작하고 실제 업무 자료를 입력하지 않는다.

## 권장 학습 순서와 짧은 실험

각 실험은 **제안이며 아직 수행하지 않았다**. 실제 비공개 업무 자료 대신 공개 예제를 사용한다.

1. 토큰·컨텍스트·작업 계약: 같은 작은 코드에 모호한 요청과 완료 조건이 있는 요청을 주고 차이를 기록한다. 15분.
2. 구조화 출력·검증: 공개 뉴스 3개의 요약에서 존재하지 않는 출처 ID와 날짜 오류를 코드로 거부해 본다. 20분.
3. 도구·권한: 읽기 도구와 파일 쓰기 도구를 구분하고 어떤 단계에 사람이 승인해야 하는지 적는다. 10분.
4. Skills·AGENTS: 현재 저장소의 지침을 읽고 `$wiki-ingest`가 어떤 자료를 읽고 어디에 쓰는지 설명한다. 15분.
5. RAG·위키: 같은 자료 2개에서 공통 주장과 상충 내용을 분리하고 각 문장에 근거 링크를 붙인다. 20분.
6. 평가·Git·CI: 작은 변경의 diff와 테스트 결과를 확인하고, 증거가 없는 완료 주장을 하나 찾아 수정한다. 15분.

## 근거 수준과 남은 질문

- 토큰·도구·출력·프로토콜·버전 관리 설명은 해당 기능을 소유한 공식 문서에 근거한다.
- RAG 설명은 원 논문에 근거한다. LLM Wiki는 작성자의 운영 패턴 제안이며 표준이나 효과 검증으로 취급하지 않는다.
- 학습 순서와 웹 개발 적용 우선순위는 이 조사에서 제안한 판단이다. 실제 팀의 성과 개선은 별도 측정이 필요하다.
- 남은 질문: 우리 팀에서 가장 반복적인 작업은 무엇이며, 정답·실패·사람 검토 기준을 작은 사례로 정의할 수 있는가?
